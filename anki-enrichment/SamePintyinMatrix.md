# Спецификация: локальная карта пиньиня 3×3 для карточек Anki

## 1. Цель

Реализовать скрипт, который обогащает китайские карточки Anki мини-картой произношения первого слога слова.

На обратной стороне карточки должна отображаться локальная область **3×3** карты китайских слогов:

* центральная клетка соответствует первому слогу текущего слова;
* горизонтальная ось — соседние finals;
* вертикальная ось — соседние initials;
* в каждой клетке отображаются ранее изученные слова, первый слог которых попадает в эту клетку;
* текущее слово выделяется в центральной клетке;
* слова с `Key >= Key текущей карточки` не должны попадать в её окружение.

Карта должна соответствовать принципу расположения слогов на:

`https://tepmex.github.io/CloudAgenticCoding/map-of-chinese/`

---

# 2. Исходные данные

Есть две колоды Anki, экспортированные в TSV.

Нумерация `Key` сквозная между колодами:

```text
Колода Refold Mandarin 1k Simplified: Key 1–1000
Колода Mandarin HSK 1000-5000: Key 1001–5000
```

Поле `Key` является глобальным порядком изучения слов.

Следовательно:

```text
карточка Key=100
может видеть только Key=1..99

карточка Key=1000
может видеть только Key=1..999

карточка Key=1001
может видеть Key=1..1000

карточка Key=3500
может видеть Key=1..3499
```

Граница между колодами не имеет значения.

С точки зрения алгоритма два TSV должны рассматриваться как **одна общая последовательность слов**.

---

# 3. Основной принцип архитектуры

Не реализовывать поиск соседей непосредственно внутри шаблона Anki.

Вместо этого:

```text
TSV A ─┐
       ├──► объединение по Key
TSV B ─┘
            │
            ▼
      разбор первого слога
            │
            ▼
      initial + final
            │
            ▼
     поиск 3×3 соседства
            │
            ▼
  только слова с меньшим Key
            │
            ▼
     генерация готового HTML
            │
            ▼
    запись PinyinMap в TSV
```

Anki должен заниматься только отображением уже подготовленного HTML.

Runtime JavaScript в карточках для построения карты не использовать.

---

# 4. Требования к входным TSV

Скрипт должен принимать произвольное количество TSV-файлов:

```bash
python build_pinyin_maps.py deck1.tsv deck2.tsv
```

Минимально необходимые поля:

```text
Key
Hanzi
Pinyin
```

Фактические названия полей должны задаваться через конфигурацию.

Например:

```python
FIELDS = {
    "key": "Key",
    "hanzi": "Hanzi",
    "pinyin": "Pinyin",
    "map": "PinyinMap",
}
```

Если `PinyinMap` отсутствует во входном TSV, скрипт должен добавить этот столбец.

Все остальные поля TSV должны быть сохранены без изменений.

Порядок строк исходных файлов желательно сохранять.

---

# 5. Глобальная последовательность

После чтения всех TSV создать общую коллекцию записей:

```python
all_notes
```

и отсортировать её:

```python
all_notes.sort(key=lambda note: note.key)
```

`Key` должен интерпретироваться как целое число.

## Проверки

Скрипт должен сообщать ошибку при:

* пустом `Key`;
* нечисловом `Key`;
* дублирующемся `Key` между любыми TSV.

Например:

```text
ERROR: duplicate Key=1247
  deck1.tsv: row ...
  deck2.tsv: row ...
```

Дублирование `Key` является ошибкой, потому что разрушает глобальный порядок изучения.

---

# 6. Что считается координатой слова

Для карты используется **только первый слог Pinyin текущего слова**.

Например:

```text
掌握    zhǎngwò
       ↓
       zhǎng

initial = zh
final   = ang
```

Другие примеры:

```text
长大       zhǎngdà       → zh | ang
长城       chángchéng     → ch | ang
学校       xuéxiào        → x  | üe
工作       gōngzuò        → g  | ong
```

Нельзя определять произношение через первый иероглиф самостоятельно.

Источником произношения является поле `Pinyin` конкретной записи.

Это необходимо для корректной работы с многозначными иероглифами:

```text
长大     zhǎngdà
长城     chángchéng
```

---

# 7. Нормализация Pinyin

Перед определением координаты необходимо:

1. выделить первый слог;
2. удалить тон для определения позиции;
3. сохранить исходный Pinyin с тоном для отображения;
4. нормализовать orthographic pinyin в систему initial/final карты.

Необходимо поддержать как минимум:

```text
ā á ǎ à
ē é ě è
ī í ǐ ì
ō ó ǒ ò
ū ú ǔ ù
ǖ ǘ ǚ ǜ
ü
u:
v
```

Например:

```text
zhǎng → zhang
xué   → xue
nǚ    → nü
```

---

# 8. Нормализация initial/final

Использовать те же фонетические принципы, что и Map of Chinese.

В частности, необходимо корректно обрабатывать:

### y / w

`y` и `w` не должны рассматриваться как обычные initials, если карта интерпретирует их как орфографические маркеры zero initial.

Например, нормализация должна корректно приводить:

```text
yi
yin
ying
you
yan

wu
wai
wei
wen
wang
```

к соответствующим underlying finals.

### ü

Корректно различать:

```text
ju
jue
juan
jun

qu
xue
```

где написанное `u` после `j/q/x` фонологически соответствует `ü`.

### apical i

Не смешивать обычное `i` со слогами:

```text
zhi
chi
shi
ri

zi
ci
si
```

Если исходная карта выделяет для них специальную final-категорию, воспроизвести эту категорию.

---

# 9. Таблица initials и finals

Не вычислять соседство через строковое сходство или расстояние Левенштейна.

Должен существовать **явно заданный порядок координат**.

Например:

```python
INITIALS = [
    "",
    "b", "p", "m", "f",
    "d", "t", "n", "l",
    "g", "k", "h",
    "j", "q", "x",
    "zh", "ch", "sh", "r",
    "z", "c", "s",
]
```

Для finals аналогично должна существовать упорядоченная таблица, соответствующая Map of Chinese.

AI-агент перед реализацией должен проверить исходный код Map of Chinese и воспроизвести порядок finals и правила нормализации максимально точно.

Порядок является частью модели данных и должен находиться в отдельном модуле, например:

```text
pinyin_map/
    layout.py
```

---

# 10. Определение 3×3

Если текущая координата:

```text
initial index = I
final index   = F
```

то окно содержит:

```text
(I-1,F-1)   (I-1,F)   (I-1,F+1)

(I,  F-1)   (I,  F)   (I,  F+1)

(I+1,F-1)   (I+1,F)   (I+1,F+1)
```

Центральная клетка:

```text
(I, F)
```

## Границы карты

Размер HTML-карты всегда должен оставаться 3×3.

Если текущая клетка находится у края глобальной карты, отсутствующая строка/колонка должна оставаться пустой.

Не сдвигать окно, чтобы искусственно заполнить 3×3.

Это позволяет сохранять ощущение положения на общей карте.

---

# 11. Невозможные слоги

Если combination `initial × final` теоретически находится внутри матрицы, но не существует в стандартном Mandarin, клетка должна отображаться пустой.

Не искать вместо неё «ближайший существующий слог».

Пример:

```text
┌────────┬────────┬────────┐
│ слово  │ слово  │   ·    │
├────────┼────────┼────────┤
│ слово  │ TARGET │ слово  │
├────────┼────────┼────────┤
│   ·    │ слово  │ слово  │
└────────┴────────┴────────┘
```

Пустые области являются частью пространственной структуры карты.

---

# 12. Историческое ограничение

Самое важное бизнес-правило:

Для карточки с:

```text
Key = N
```

разрешено показывать только записи:

```text
other.Key < N
```

Никогда:

```text
other.Key >= N
```

Это правило действует между всеми TSV.

Пример:

```text
deck1.tsv:
999  ...
1000 ...

deck2.tsv:
1001 新词
```

При построении карты для `Key=1001` слова из первой колоды должны использоваться как обычные ранее изученные слова.

# 13. Рекомендуемый алгоритм

Обрабатывать слова один раз в порядке `Key`.

Хранить bucket для каждой фонетической клетки:

```python
buckets[(initial, final)] = [...]
```

Псевдокод:

```python
notes = load_all_tsv_files()
notes.sort(key=lambda n: n.key)

buckets = {}

for note in notes:

    syllable = parse_first_syllable(note.pinyin)
    cell = normalize_to_cell(syllable)

    neighbourhood = get_3x3(cell)

    html = render_map(
        current_note=note,
        neighbourhood=neighbourhood,
        buckets=buckets,
    )

    note.pinyin_map = html

    # ВАЖНО: добавлять текущее слово только ПОСЛЕ render_map.
    buckets.setdefault(cell, []).append(note)
```

Последовательность:

```python
render_map(...)
buckets[cell].append(note)
```

критична.

Благодаря этому для `Key=N` содержимое `buckets` автоматически содержит только:

```text
Key < N
```

Не нужно выполнять отдельный SQL-подобный поиск для каждой карточки.

---

# 14. Какие слова показывать внутри клетки

Количество слов должно быть ограничено, иначе распространённые клетки быстро переполнятся.

Значения сделать конфигурируемыми:

```python
MAX_CENTER_PREVIOUS_WORDS = 4
MAX_NEIGHBOUR_WORDS = 3
```

Предпочтительный алгоритм выбора:

### Соседние клетки

Показывать последние изученные слова:

```python
bucket[-MAX_NEIGHBOUR_WORDS:]
```

То есть слова с максимальными `Key`, но всё ещё:

```text
Key < current.Key
```

### Центральная клетка

Показывать:

1. текущее слово;
2. до `MAX_CENTER_PREVIOUS_WORDS` ранее изученных слов той же клетки.

Текущее слово не считается «предыдущим» и всегда присутствует.

# 15. Отображаемые данные слова

Минимально в каждой клетке показывать Hanzi.

Например:

```text
张
长
账
```

Опционально при наличии пространства:

```text
张
zhāng
```

Рекомендуемый вариант:

* соседние клетки: Hanzi;
* центральное текущее слово: Hanzi + Pinyin первого слога;
* прошлые слова центральной клетки: Hanzi.

Полный Pinyin всего слова в мини-карте обычно не нужен.

---

# 16. Счётчик скрытых слов

Если bucket содержит больше слов, чем разрешено показать, добавить:

```text
+N
```

Например:

```text
张
长
账
+7
```

означает, что в этой клетке ранее изучено ещё семь слов.

Расчёт:

```python
hidden_count = len(bucket) - displayed_count
```

Не включать текущее слово в `hidden_count`.

# 18. Оси

Хотя логическая карта имеет размер 3×3, HTML должен дополнительно показывать подписи осей.

Получается визуальная сетка:

```text
             final-1   final   final+1

initial-1      □         □         □

initial        □       TARGET      □

initial+1      □         □         □
```

Подписи initials должны находиться слева.

Подписи finals — сверху.

Это позволяет пользователю видеть не только соседей, но и конкретное «место на карте»:

```text
zh + ang
```

# 19. CSS

Подготовить отдельный файл с CSS, который пользователь сможет добавить в Anki Styling.

Требования:

* адаптивность для desktop и mobile;
* ширина карты порядка `320–450px`;
* отсутствие horizontal scroll;
* читаемость в светлой и тёмной теме;
* центр визуально выделен;
* соседние клетки второстепенны относительно основного содержимого карточки;
* не использовать фиксированные цвета фона, плохо работающие в night mode.

Рекомендуемая структура:

```css
.pm {}

.pm-grid {}

.pm-final {}
.pm-initial {}

.pm-cell {}
.pm-cell--center {}
.pm-cell--empty {}

.pm-current {}
.pm-current-pinyin {}

.pm-word {}
.pm-more {}
```

Можно использовать CSS Grid.

# 20. Поле PinyinMap

Итоговое вычисляемое поле:

```text
PinyinMap
```

не является источником данных.

Его всегда можно полностью пересоздать на основании:

```text
Key
Hanzi
Pinyin
```

и глобальной структуры карты.

Поэтому повторный запуск скрипта должен просто перезаписывать старое значение.

# 21. Формат вывода

По умолчанию **не изменять исходные TSV**.

Создавать:

```text
deck1.with-pinyin-map.tsv
deck2.with-pinyin-map.tsv
```

Например:

```bash
python build_pinyin_maps.py deck1.tsv deck2.tsv
```

результат:

```text
output/
    deck1.with-pinyin-map.tsv
    deck2.with-pinyin-map.tsv
```

Поддержать явный флаг для изменения файлов на месте:

```bash
python build_pinyin_maps.py deck1.tsv deck2.tsv --in-place
```

но не использовать его по умолчанию.

# 22. Сохранение принадлежности к TSV

После объединения записей для вычисления истории необходимо помнить, из какого файла была прочитана каждая строка.

Например:

```python
NoteRecord:
    source_file
    source_row
    key
    hanzi
    pinyin
    fields
    pinyin_map
```

После генерации результаты должны вернуться в соответствующий TSV.

То есть объединение файлов используется только для вычислений.

Не создавать один объединённый TSV вместо исходных файлов, если пользователь явно этого не попросил.

---

# 23. Парсинг TSV

Нужно корректно учитывать особенности Anki export:

* UTF-8;
* табуляция как separator;
* HTML внутри полей;
* пустые значения;
* потенциальные служебные строки Anki в начале файла.

Перед реализацией агент должен посмотреть реальные входные TSV и определить их формат.

Если присутствуют строки вида:

```text
#separator:tab
#html:true
#notetype column:...
```

они должны быть сохранены.

---

# 24. Обработка ошибок Pinyin

Если Pinyin невозможно распарсить, скрипт не должен падать полностью.

Необходимо:

1. записать предупреждение;
2. оставить `PinyinMap` пустым для этой записи;
3. не добавлять такую запись в buckets.

Пример:

```text
WARNING Key=1742:
cannot parse first syllable from Pinyin="..."
```

В конце вывести summary:

```text
Processed: 5000
Maps generated: 4978
Skipped: 22
Warnings: 22
```

# 27. Тесты

Обязательно написать automated tests.

## Историческое ограничение

Дано:

```text
1   A   zhāng
2   B   zhǎng
3   C   zhàng
```

Для `Key=2` допустимо отображать:

```text
A
```

но нельзя:

```text
C
```

Для `Key=3` допустимы:

```text
A
B
```

---

## Граница между колодами

TSV A:

```text
999
1000
```

TSV B:

```text
1001
1002
```

Карта `Key=1001` должна иметь доступ к словам:

```text
1..1000
```

включая строки из TSV A.

---

## Независимость от порядка TSV

Эти два запуска должны давать идентичные результаты:

```bash
script deck1.tsv deck2.tsv
```

и:

```bash
script deck2.tsv deck1.tsv
```

Глобальный порядок определяется исключительно `Key`.

---

## Независимость от порядка строк

Перемешивание строк внутри TSV не должно менять карту.

---

## Polyphonic Hanzi

```text
长大       zhǎngdà
长城       chángchéng
```

должны попасть в разные клетки.

---

## Tones

```text
zhāng
zháng
zhǎng
zhàng
```

должны иметь одну координату:

```text
zh|ang
```

---

## ü

Проверить как минимум:

```text
lü
lǜ
ju
```

# 28. Производительность

Для примерно 5000 слов выполнение должно быть практически мгновенным.

Не использовать алгоритм:

```text
для каждого слова:
    просмотреть все предыдущие слова
```

сложности `O(N²)`.

Использовать buckets.

Ожидаемая сложность примерно:

```text
O(N log N)
```

из-за сортировки по `Key`, после чего обработка:

```text
O(N)
```

# 30. Разделение ответственности модулей

## `parser.py`

Отвечает только за:

```text
Pinyin → первый слог → normalized initial/final
```

Не знает о TSV и `Key`.

---

## `layout.py`

Содержит:

```text
INITIALS
FINALS
valid cells
правила порядка карты
```

---

## `neighbourhood.py`

Реализует:

```text
coordinate → 3×3 coordinates
```

---

## `renderer.py`

Получает уже готовые данные и создаёт HTML.

Не занимается фонетическим анализом.

---

## `tsv.py`

Читает и записывает Anki TSV, сохраняя все неизвестные поля.

---

## `build_pinyin_maps.py`

Оркестрирует:

```text
load
→ validate
→ sort
→ calculate
→ render
→ save
```

# 31. Желательно не зашивать схему конкретной колоды

Добавить конфигурацию через CLI:

```bash
python build_pinyin_maps.py \
  deck1.tsv deck2.tsv \
  --key-field Key \
  --hanzi-field Hanzi \
  --pinyin-field Pinyin \
  --map-field PinyinMap
```

Значения по умолчанию могут быть:

```text
Key
Hanzi
Pinyin
PinyinMap
```

# 32. HTML escaping

Данные из TSV необходимо корректно HTML-escape-ить перед вставкой в `PinyinMap`.

Например Hanzi или другие поля не должны позволять сломать структуру HTML.

Сам генерируемый HTML после этого записывается в поле как HTML.

---

# 33. Детерминированность

При одинаковых входных TSV результат должен быть byte-for-byte одинаковым.

Не использовать:

* случайную выборку соседей;
* текущую дату;
* Anki review state;
* текущий due;
* ease;
* interval.

Единственный временной порядок:

```text
Key
```

---

# 34. Что специально НЕ входит в первую версию

Не реализовывать в MVP:

* изменение `.anki2` SQLite напрямую;
* Anki add-on;
* JavaScript-поиск соседей во время review;
* анализ статистики повторений;
* автоматическое определение порядка изучения по Anki revlog;
* изменение карты в зависимости от текущей зрелости карточки;
* кликабельные переходы между карточками;
* sound playback;
* tone coloring.

Эти возможности могут быть добавлены позже.

Первая версия должна быть простым надёжным преобразователем:

```text
TSV + TSV → enriched TSV + enriched TSV
```

# 36. Критерии готовности MVP

Задача считается выполненной, если:

1. Скрипт принимает как минимум два TSV.
2. Объединяет их логически по глобальному `Key`.
3. Корректно извлекает первый слог Pinyin.
4. Определяет его initial/final.
5. Использует layout, совместимый с Map of Chinese.
6. Строит 3×3 вокруг текущей клетки.
7. Для `Key=N` использует исключительно слова `Key<N`.
8. История работает через границу двух колод.
9. Центральная клетка содержит текущее слово.
10. В остальных клетках показываются только ранее изученные слова.
11. Количество слов на клетку ограничено.
12. Генерируется готовый HTML.
13. Результат записывается в `PinyinMap`.
14. Исходные TSV по умолчанию не изменяются.
15. Есть unit tests.
16. Есть `--debug-key`.
17. Есть CSS для Anki.
18. Есть README.
19. Запуск на одних и тех же данных детерминирован.
20. Все 5000 строк обрабатываются без квадратичного поиска.

# 37. Важное уточнение для агента

Не трактовать две Anki-колоды как две независимые истории обучения.

Правильная модель:

```text
                   GLOBAL LEARNING HISTORY

deck A
Key 1 ─────────────────────────────── Key 1000
                                             │
                                             ▼
deck B
                                      Key 1001 ───────── Key 5000
```

То есть при вычислении карты:

```text
source deck ≠ learning boundary
```

Единственной границей доступных пользователю слов является:

```python
previous_word.key < current_word.key
```

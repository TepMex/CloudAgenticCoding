Ты — инженерный ИИ-агент. Твоя задача — разработать безопасный и воспроизводимый способ обогатить существующую коллекцию Anki новыми данными, **не потеряв и не сбросив прогресс обучения существующих карточек**.

## Главный принцип

Существующие notes/cards Anki нельзя пересоздавать без необходимости.

Нужно:

* сохранять существующие note IDs и card IDs;
* сохранять scheduling information, интервалы, ease, историю повторений и состояние карточек;
* обновлять поля существующих notes;
* при необходимости добавлять новые поля в существующие Note Types;
* не удалять и не импортировать заново существующие карточки;
* не использовать прямое изменение SQLite-базы Anki, если задачу можно выполнить через Anki/AnkiConnect.

Предпочтительный интерфейс автоматизации — **AnkiConnect + Python**.

Перед любыми массовыми изменениями обязательно предусмотри резервную копию коллекции.

---

# Что нужно сделать

Я хочу обогатить существующие заметки Anki дополнительными данными.

Типичные операции:

1. Добавить русский перевод английского значения слова.
2. Добавить русский перевод английского примера.
3. Добавить похожие слова:

   * близкие по значению;
   * легко путаемые;
   * при необходимости противоположные;
   * кратко объяснить разницу в употреблении.
4. Найти фразы и слова без озвучки.
5. Сгенерировать для них аудио через облачный TTS.
6. Добавить сгенерированные аудиофайлы в Anki media collection.
7. Записать ссылки вида `[sound:filename.mp3]` в соответствующие поля.
8. Не перезаписывать уже существующие качественные данные без необходимости.
9. Сделать процесс безопасно перезапускаемым.

# Сначала исследуй коллекцию

Не предполагай заранее структуру моих Note Types.

Сначала через AnkiConnect:

1. Получи список колод.
2. Получи Note Types, используемые в целевой колоде.
3. Получи список их полей.
4. Получи шаблоны карточек.
5. Возьми небольшую выборку реальных notes и изучи фактическую структуру данных.
6. Определи:

   * где хранится слово;
   * где английское определение;
   * где пример;
   * где существующее аудио;
   * какие поля уже содержат переводы или дополнительные сведения.

После исследования предложи mapping существующих и новых полей.

Не начинай массовую обработку до того, как структура станет понятна.

# Сохранение прогресса

Это критическое требование.

При реализации постоянно проверяй, что:

* существующая note обновляется через её существующий ID;
* существующая card не пересоздаётся;
* scheduling не изменяется;
* review history не изменяется;
* deck assignment не меняется без необходимости.

Для обновления содержимого используй операции типа `updateNoteFields`.

Не используй схему:

`export → удалить → импортировать заново`.

Не используй создание новой note вместо обновления существующей.

# Обработка одной note

Pipeline одной заметки должен выглядеть примерно так:

```text
existing Anki note
        ↓
read fields
        ↓
determine missing enrichment
        ↓
LLM enrichment
        ↓
TTS if needed
        ↓
store media
        ↓
update existing note fields
        ↓
mark enrichment version/status
```

Обработка должна быть **идемпотентной**.

Повторный запуск не должен:

* повторно переводить уже обработанный текст;
* заново генерировать тот же TTS;
* создавать дубли аудиофайлов;
* многократно добавлять одни и те же похожие слова;
* портить данные после частично завершённого запуска.

# LLM enrichment

По возможности отправляй связанные данные одним запросом.

Например, вход:

```json
{
  "word": "concede",
  "definition_en": "to admit that something is true",
  "example_en": "He eventually conceded that she was right."
}
```

Ожидай строго структурированный JSON примерно такого вида:

```json
{
  "definition_ru": "признать, что что-либо является правдой",
  "example_ru": "В конце концов он признал, что она была права.",
  "similar_words": [
    {
      "word": "admit",
      "difference": "ближайший аналог; часто используется для признания факта"
    },
    {
      "word": "acknowledge",
      "difference": "подчёркивает признание существования или истинности факта"
    }
  ],
  "contrast_words": [
    {
      "word": "deny",
      "difference": "противоположное значение — отрицать"
    }
  ]
}
```

Парсинг ответа должен быть строгим.

Если JSON невалиден:

* не записывай частичный мусор в Anki;
* повтори запрос с исправлением либо отметь ошибку;
* логируй проблему.

# Правила для переводов

Перевод должен соответствовать именно тому значению слова, которое описано в текущей note.

Не нужно выдавать полный словарный список всех значений слова, если карточка посвящена одному конкретному значению.

Русский текст должен быть:

* естественным;
* кратким;
* пригодным для карточки Anki;
* семантически точным;
* без ненужных пояснений, если они не помогают изучению.

Для примеров сохраняй смысл, стиль и время исходной фразы.

---

# Similar words

Не ограничивайся формальными синонимами.

Цель — помочь изучающему язык различать близкие слова.

Предпочтительный формат:

```text
admit — ближайшее по смыслу; признать факт
acknowledge — признать или подтвердить существование факта
yield — уступить; пересекается только в части контекстов
deny — противоположное значение
```

Количество — обычно 2–5 наиболее полезных слов.

Не добавляй длинные списки тезауруса.

# TTS

TTS должен генерироваться только там, где аудио отсутствует.

Поддержи возможность выбора провайдера через конфигурацию, например:

* OpenAI TTS;
* Google Cloud TTS;
* Azure Speech;
* AWS Polly;
* другой API.

Не привязывай основную бизнес-логику к одному провайдеру.

Желательно сделать интерфейс вроде:

```python
class TTSProvider:
    def synthesize(self, text: str, language: str) -> bytes:
        ...
```

---

# Кеш TTS

Не синтезируй один и тот же текст повторно.

Для имени аудиофайла используй стабильный hash, зависящий минимум от:

* текста;
* языка;
* голоса;
* TTS-провайдера;
* при необходимости настроек модели.

Например:

```text
tts_en_1f47ac9812.mp3
```

Перед TTS проверяй:

1. есть ли запись в локальном кеше;
2. существует ли уже такой media-файл в Anki;
3. только затем обращайся к API.

# Media

Добавляй аудиофайлы штатным способом через AnkiConnect.

После загрузки записывай в поле:

```text
[sound:tts_en_1f47ac9812.mp3]
```

Не используй абсолютные пути к локальным файлам.

---

# EnrichmentVersion

Система должна поддерживать повторные улучшения в будущем.

Например:

```text
EnrichmentVersion = 1
```

Позже я могу изменить prompt или алгоритм и запустить:

```text
TARGET_ENRICHMENT_VERSION = 2
```

Тогда можно найти только старые notes и обработать их повторно.

При этом новая версия не должна автоматически уничтожать вручную исправленные мной данные.

Продумай стратегию обновления.

# Защита пользовательских данных

По умолчанию заполняй только:

* либо поля, явно разрешённые для автоматического обновления.

# Backup

Перед массовой записью:

1. предупреди меня, что нужно создать backup;
2. желательно проверь или реализуй экспорт/backup, если это возможно безопасно;
3. не полагайся только на возможность Undo.

Рекомендуемый backup — полный экспорт коллекции Anki с scheduling information.

# Ошибки

Ошибка при обработке одной note не должна останавливать всю коллекцию.

Поведение:

```text
try note
→ success → save
→ failure → log error → continue
```

Но ошибки инфраструктуры, например недоступный AnkiConnect, должны приводить к остановке до начала обработки.

---

# Rate limits и стоимость

Для LLM/TTS:

* добавь retry с exponential backoff;
* учитывай rate limits;
* не делай бесконечных retry;
* кешируй результаты;
* желательно считай количество API-вызовов.

Перед обработкой всей коллекции покажи примерную оценку:

```text
Notes requiring LLM: 1240
Sentences requiring TTS: 617
Cached TTS: 183
New TTS requests: 434
```

Если точную стоимость определить нельзя, достаточно количества вызовов.

# Работа по этапам

Работай последовательно.

## Этап 1 — аудит

Исследуй текущую коллекцию и покажи:

* колоды;
* Note Types;
* поля;
* пример нескольких notes;
* рекомендуемую mapping-схему.

## Этап 2 — проектирование

Предложи минимальную архитектуру и объясни, какие поля будут добавлены.

## Этап 3 — реализация

Создай рабочий код.

Не ограничивайся псевдокодом, если среда позволяет написать реальный код.

## Этап 4 — dry run

Запусти на небольшой выборке без записи и покажи результат.

## Этап 5 — тестовая запись

Обработай максимум несколько notes.

После обработки проверь через AnkiConnect, что:

* note ID сохранился;
* card IDs сохранились;
* новые поля появились;
* scheduling карточек не изменился.

## Этап 6 — массовый запуск

Только после успешной проверки подготовь команду для обработки всей целевой колоды.

# Критерий готовности

Задача считается выполненной, когда существует инструмент, который можно безопасно запускать повторно примерно так:

```bash
python main.py --query 'deck:"English"' --enrich
```

и он:

* находит существующие notes;
* определяет недостающие данные;
* получает enrichment;
* при необходимости делает TTS;
* добавляет media;
* обновляет **существующие** notes;
* не пересоздаёт cards;
* не сбрасывает scheduling;
* кеширует результаты;
* переживает частичные сбои;
* позволяет продолжить обработку после остановки.

Во всех спорных ситуациях приоритет такой:

**сохранность моей существующей коллекции и прогресса > автоматизация > скорость обработки.**

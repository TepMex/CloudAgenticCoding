# Архитектура ear-eye-t

Один модуль `app`. Чистая логика интервалов лежит в `dev.eareye.t.domain` и не импортирует Android, поэтому её гоняют обычные JVM-тесты. Сбор, Room и Compose зависят от платформы.

## Что говорят публичные API

Проверено по документации Android и исходному коду AOSP (ветка main на момент реализации).

**Экран.** `UsageStatsManager.queryEvents(UsageEventsQuery)` добавлен в API 35. `UsageEventsQuery.Builder.setEventTypes(int...)` ограничивает выборку. На API 28–34 используется `queryEvents(begin, end)`, лишние типы отбрасываются на клиенте. События система хранит несколько дней. С Android R запрос возвращает `null`, пока пользователь не разблокирован (`UserManager.isUserUnlocked()`). Пустой или `null`-результат не затирает уже сохранённое окно. Доступ — app-op `PACKAGE_USAGE_STATS` через `Settings.ACTION_USAGE_ACCESS_SETTINGS`, не runtime permission.

**Звук.** У обычного приложения публичны `AudioManager.getActivePlaybackConfigurations()`, `registerAudioPlaybackCallback()` и `AudioPlaybackConfiguration.getAudioAttributes()`. `isActive()` и `getPlayerState()` помечены `@hide` / `@SystemApi`. Их нет в публичном справочнике, и код их не вызывает.

В `PlaybackActivityMonitor.anonymizeForPublicConsumption()` в публичный список попадают только конфигурации, для которых скрытый `isActive()` истинен. По AOSP это `PLAYER_STATE_STARTED` и не выключенный клиентской громкостью, volume shaper или app-op. Пауза в список не входит. Идентификаторы чужого приложения вырезаются при анонимизации, поэтому имена плееров не запрашиваются.

Следствие, которое нужно проверить на HONOR: нулевая громкость может убрать плеер из публичного списка. Это поведение платформы, а не дополнительный фильтр приложения. Список сообщает об активности плеера, не о слышимости. Без микрофона тишину и тихий сигнал не отличить.

**Служба уведомлений.** Включён ли доступ, проверяется публичным `NotificationManager.isNotificationListenerAccessGranted(ComponentName)`. Константы `Settings.Secure.ENABLED_NOTIFICATION_LISTENERS` в публичном SDK 36 нет, содержимое уведомлений не читается. `requestRebind(ComponentName)` документирован как полезный только после `requestUnbind()` того же процесса. Приложение `requestUnbind()` не вызывает и `requestRebind()` не использует. Пока доступ включён, систему просят связать службу обычным путём. Если связь пропала, пользователь заново открывает экран доступа.

**Фон.** Периодический WorkManager не является точным будильником. Exact alarm и wake lock не используются. Heartbeat — `Handler.postDelayed` на фоновом потоке раз в 5 минут. Doze может его задержать.

## Поток данных

1. `ScreenSyncWorker` и запуск процесса читают UsageEvents в перекрывающееся окно (первый раз — 7 суток, дальше — час до доверенного горизонта). В транзакции события окна заменяются. Горизонт доверия сдвигается только после успешного чтения.
2. `MonitoringNotificationListenerService.onListenerConnected()` закрывает оборванную сессию на последнем подтверждении, открывает новую, регистрирует callback и на том же `Handler` читает снимок. Повторная регистрация отсекается флагом.
3. `AudioAggregateReducer` хранит один бит «есть хотя бы один подходящий плеер». `ACTIVE → ACTIVE` и `INACTIVE → INACTIVE` записей не создают.
4. `MonitoringHealthTracker` сравнивает соседние пробы wall-clock и `elapsedRealtime`. Другой `BOOT_COUNT` — перезагрузка. Расхождение часов больше 5 секунд — разрыв сессии и новый снимок. Пауза монотонных часов больше 30 минут — неизвестный промежуток, даже если процесс ещё считает себя живым.
5. `reconstructEye` и `reconstructEar` строят интервалы из сырых строк. `calculateDailyStatistics` считает метрики. UI их не хранит отдельным счётчиком, поэтому день можно пересчитать.

## Метрики

Регион, где известны и экран, и звук:

- Eye Only, Ear Only, Overlap и Union считаются только в нём.
- `Union = Eye + Ear − Overlap` проверяется на этом регионе.
- Глазное время, попавшее в дыру аудио, показывается отдельно и не называется «только экран».
- Дыра аудио — «возможно не учтено», не ноль.

Покрытие на экране — доля периода, в которой состояние звука известно: сессия мониторинга или пара shutdown/startup. Время после последнего подтверждения оборванной сессии в покрытие не входит.

Сегодняшний период заканчивается «сейчас», а не полуночью. Будущий день пустой.

## Почему не Foreground Service в первой версии

Гипотеза MVP: система сама держит `NotificationListenerService`, пока пользователь включил доступ. Постоянное уведомление и тип FGS не нужны.

Сравнение с `foregroundServiceType="specialUse"` на Android 14–16:

- С API 34 у FGS обязателен тип. `specialUse` требует объявления и на устройствах с политикой Play — отдельного обоснования. Локальный APK это не отменяет: система всё равно ограничивает запуск FGS из фона.
- Тип `mediaPlayback` здесь был бы ложным: приложение само ничего не играет.
- `dataSync` и похожие типы ограничены по времени и не рассчитаны на многочасовое слушание callback.
- На Android 15–16 старт FGS из фона сужен ещё сильнее. Служба, которую система связывает сама, этому правилу не противоречит.
- Цена гипотезы: MagicOS может убить связанную службу вместе с процессом. Тогда появляется неизвестный промежуток. Это предпочтительнее, чем выдуманное продолжение звука. FGS можно рассмотреть после замеров на HONOR, отдельным решением, без смены типа на `mediaPlayback`.

## Риски

1. Круглосуточная живучесть Notification Listener на MagicOS 10 не проверена на устройстве.
2. Force-stop не равен убийству процесса. После force-stop система может не поднимать службу до ручного запуска.
3. `onDestroy()` может не вызваться. Следующий старт закрывает сессию как неожиданную на последнем heartbeat, callback или снимке.
4. Большой heartbeat не доказывает смерть службы, но и не доказывает непрерывное наблюдение. Порог 30 минут — параметр честности, не измеренная погрешность.
5. У retention UsageEvents есть предел. Если телефон был выключен дольше, чем система хранит события, дыру без `DEVICE_STARTUP` нельзя отличить от «ничего не менялось». Длинное выключенное состояние без событий само по себе неизвестностью не считается: иначе многочасовое чтение без новых событий превратилось бы в дыру.
6. AOD на части прошивок может прийти как `SCREEN_INTERACTIVE`. На стандартном Android AOD — это `SCREEN_NON_INTERACTIVE`. Поведение HONOR надо смотреть в тесте.
7. Скачок часов кладёт новый кусок на новый wall-clock якорь. Пропущенный скачком диапазон epoch не переживается как реальное время; в статистике он выглядит как разрыв наблюдения.
8. OEM может не положить браузер, Bluetooth или игру в публичный список так, как AOSP. Тест M это проверяет.
9. Очень короткий звук может закончиться раньше, чем система пришлёт callback. Искусственной задержки на конце интервала нет.
10. Нулевая громкость может выглядеть как отсутствие плеера. См. AOSP `isActive()` выше.

## Энергия

Нет wake lock, GPS, микрофона, Accessibility, MediaProjection, exact alarm, сети и опроса раз в 1–5 секунд. Запись в базу — на переходе состояния, на heartbeat раз в 5 минут (одна строка сессии) и на синхронизации экрана. UI обновляет открытый интервал таймером 30 секунд только пока экран приложения подписан на Flow.

Процент батареи без профилирования не заявляется. Как мерить — в README.
